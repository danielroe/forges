If you are writing a CLI or a server that should work with whichever forges a user has credentials for, it would be tedious to write configuration code for each one. `forges/env` solves this by creating providers from environment variables. Every variable follows the form `FORGES_<KIND>_<FIELD>`, such as `FORGES_GITHUB_TOKEN` or `FORGES_GITLAB_BASE_URL`, and the forges that have variables set are the ones you get.

## Create the providers

To turn the variables into providers, pass them to `forgesFromEnv()`. It reads every set of variables, builds a provider for each forge that is configured and hands them all to `createForges()`:

```ts
import { forgesFromEnv } from 'forges/env'

const forges = forgesFromEnv(process.env)
```

## Report skipped forges

`forgesFromEnv()` silently leaves out any set of variables that can't configure a provider, for example because the token is missing. If you would rather tell the user, use `providersFromEnv()` instead. It returns one entry for each set of variables. An entry has a `factory` when the variables are enough to configure a provider, and a `skipped` reason when they aren't. The reason never contains a credential, so it is safe to log:

```ts
import { createForges } from 'forges'
import { providersFromEnv } from 'forges/env'

const entries = providersFromEnv(process.env)

for (const entry of entries) {
  if (entry.skipped) {
    console.warn(`Skipping ${entry.forge}: ${entry.skipped}`)
  }
}

const forges = createForges(
  entries.flatMap(entry => entry.factory ? [entry.factory] : []),
)
```

## Variables

In the variable names, `<KIND>` is the name of the forge in upper case, with an underscore in place of a hyphen. That gives `GITHUB`, `GITLAB`, `BITBUCKET`, `FORGEJO`, `GITEA`, `GITEE`, `AZURE_DEVOPS`, `CURSOR_ORIGIN`, `TANGLED` and `PUSHIN`.

The following fields work for every forge. Most of them set the provider option of the same name, and the table describes what each one does:

| Field | Effect |
| --- | --- |
| `TOKEN` | Sets `auth` to a token |
| `BASE_URL` | Sets `baseUrl` |
| `INSTANCE` | Sets `instance` |
| `INSTANCE_VERSION` | Sets `instanceVersion` |
| `WEBHOOK_SECRET` | Sets `webhookSecret` |
| `READ_ONLY` | Sets `readOnly: true` when the value is `1` or `true` |
| `ENABLED` | `1` or `true` creates an anonymous provider without a token. `0` or `false` skips the forge |
| `DEMO_REPO` | Sets `entry.demoRepo` to an `owner/name` repository for your code to use, and enables anonymous reads |

A few forges need more than that, so they read additional fields:

| Forge | Fields |
| --- | --- |
| GitHub, Cursor Origin | `APP_ID`, `PRIVATE_KEY` and `INSTALLATION_ID` for app auth. Write the newlines in `PRIVATE_KEY` as `\n` |
| Bitbucket, Azure DevOps | `USERNAME` and `PASSWORD` for Basic auth |
| Azure DevOps | `ORGANIZATION`, which is required |
| Tangled | `IDENTIFIER`, `PASSWORD` and an optional `PDS` for an app password. `API_URL` and `NOTIFICATIONS_URL` set the service URLs |

To learn what these options do on a particular forge, see its [provider page](/providers).

## Configure a second instance

You might have credentials for two instances of one forge, such as github.com and a company's GitHub Enterprise Server. To configure the second one, add a suffix after the field name. This starts a new set of variables for the same forge. Every variable in a set carries the same suffix, and you can read it from `entry.suffix`:

```sh
FORGES_GITHUB_TOKEN=ghp_...
FORGES_GITHUB_TOKEN_WORK=ghp_...
FORGES_GITHUB_BASE_URL_WORK=https://ghe.example.com/api/v3
```

As with any other registration, `createForges()` throws when two providers share a forge and an instance. If two sets of variables point at the same host, give one of them a different `INSTANCE`.
