When a request fails, the call rejects with a typed error. All of these errors extend `ForgeError`, so you can catch the base class to handle everything in one place, or narrow down with `instanceof` when a specific failure needs its own response:

```ts
import { ForgeError, NotFoundError, RateLimitedError, TokenRevokedError } from 'forges'

try {
  await gh.threads.close(thread.ref)
}
catch (error) {
  if (error instanceof NotFoundError) {
    console.warn('The thread is gone, or the token cannot see it')
  }
  else if (error instanceof RateLimitedError) {
    console.warn(`Rate limited until ${error.resetAt?.toISOString()}`)
  }
  else if (error instanceof TokenRevokedError) {
    await askForNewToken()
  }
  else if (error instanceof ForgeError) {
    console.error(error.forge, error.url, error.message)
  }
  else {
    throw error
  }
}
```

If a failure came from a request, the error tells you where it happened with `forge`, `instance`, `url` and `method`. `ForgeApiError` and its subclasses go further and add the `status` of the response and a truncated `body`. You can find every error class in the [error reference](/reference/errors).

## Rate limits

Forges limit how many requests you can send, and they tell you when you have to wait. If a forge rate-limits a request and asks for a pause of one minute or less with `retry-after`, the provider waits that long and tries the request once more, so most short limits never reach your code. To see when this happens, pass `onRetry`. It is called with the `url`, the `method` and the `wait` in milliseconds, which makes it a good place to log or count retries:

```ts
const forge = github({
  auth,
  onRetry: ({ method, url, wait }) =>
    console.warn(`Retrying ${method} ${url} in ${wait} ms`),
}).create()
```

If the wait is longer than a minute, or the retry runs into a limit again, the call rejects with `RateLimitedError`. Its `resetAt` property tells you when the limit resets. `secondary` is `true` when the forge applied an abuse limit, which has no request counter that you could check.

To see how much of your budget is left, read `page.rateLimit` after a listing. It reports what the forge sent along with the response. To follow the budget across every call, including calls that don't return a page, pass `onRateLimit`. It is called with the `url`, the `method` and the `rateLimit` of each response that reports one:

```ts
const forge = github({
  auth,
  onRateLimit: ({ rateLimit }) =>
    console.info(`${rateLimit.resource}: ${rateLimit.remaining} left`),
}).create()
```

Some forges keep several budgets. GitHub, for example, counts search and GraphQL requests apart from the rest of its API, so `rateLimit.resource` names the budget that the response used, such as `core`, `search` or `graphql`.

## Unsupported operations

If you call an operation that the forge doesn't offer, the call rejects with `UnsupportedOperationError`. You can avoid it by checking the operation with [`can()`](/guides/capabilities) first.

## Warnings

Not every problem is serious enough to fail a call. A listing might skip an item that it couldn't read, or ignore a filter that the forge doesn't have. In these cases the provider finishes the call and reports the problem as a warning instead. Each warning has a stable `code`, such as `filter_unsupported` or `thread_unreadable`, so you can handle it in code.

You can read `warnings` from a page, and also from an iterable, either while you iterate or after you have finished:

```ts
const threads = gh.threads.list(repo, { sort: 'comments' })

for await (const thread of threads) {
  render(thread)
}

for (const warning of threads.warnings) {
  console.warn(warning.code, warning.message)
}
```

## Timeouts

Every provider has a `timeout`. A request that takes longer rejects with `ForgeTimeoutError`. If a request never gets a response at all, for example because of a DNS or TLS failure, it rejects with `ForgeNetworkError`.

## Retrying writes

When a write fails with `ForgeTimeoutError`, `ForgeNetworkError` or a `ForgeApiError` with a 5xx `status`, you can't tell whether the forge applied it. None of the forges that `forges` supports accepts an idempotency key on these writes, so the library can't make a retry safe for you, and providers never retry a write on their own, except after a rate limit, where the forge refused the request. Whether you can send the write again depends on what a second attempt does:

| Verb | What a repeat does | What to do |
| --- | --- | --- |
| `threads.close()`, `threads.reopen()` | Leaves the same state. On Tangled, each call writes another state record | Retry |
| `threads.update()` | Leaves the same state. Where it makes several requests, a failure can leave the earlier fields changed, and a repeat sets the rest | Retry |
| `threads.setLabels()`, `addLabels()`, `removeLabels()`, `setAssignees()`, `setMilestone()` | Leaves the same state | Retry |
| `threads.requestReview()` | Leaves the same state. On GitLab and Bitbucket it reads the reviewers and writes them back with yours added, so a change that someone else makes in between is lost | Retry |
| `threads.react()`, `threads.unreact()`, `threads.markDuplicate()` | Leaves the same state | Retry |
| `threads.editComment()`, `releases.update()`, `webhooks.update()`, `webhooks.rotateSecret()` | Leaves the same state | Retry |
| `threads.subscribe()`, `threads.unsubscribe()`, `threads.resolveReviewThread()`, `threads.unresolveReviewThread()` | Leaves the same state | Retry |
| `notifications.markRead()` and the other notification writes | Leaves the same state | Retry |
| `repos.addCollaborator()` | Leaves the same state. GitLab rejects it once the account is a member | Check `repos.permissionFor()` first |
| `threads.deleteComment()`, `webhooks.delete()` | Can reject with `NotFoundError` | Treat `NotFoundError` on a retry as done |
| `threads.merge()` | Rejects once the pull request has merged | Pass `sha`, and read the pull request after any failure |
| `threads.submitReview()` | Can reject once the review is submitted | Read it with `threads.getReview()` first |
| `threads.transfer()` | Can reject once the thread has moved | Look for it in the target repository first |
| `repos.createLabel()` | Rejects, because the name is taken. Tangled adds a second label with the same name | Look for the name in `repos.labels()` first |
| `releases.create()` | Rejects for a tag that already has a release | Read it with `releases.getByTag()` first |
| `contents.commitFiles()` | With `expectedHead`, rejects with `BranchMovedError` once the first attempt has moved the branch. With `createFrom`, rejects once the branch exists. Without either, adds a second commit | Pass `expectedHead`, and on `BranchMovedError` read the branch to see whether its head is your commit |
| `threads.comment()` | Posts a second comment | Pass a `key`, and retry with `upsertComment()`, as described below |
| `threads.create()` | Creates a second issue or discussion. Most forges reject a second open pull request from the same `head` to the same `base`, but Tangled creates one | Look for it with `threads.list()` first |
| `threads.createReview()`, `threads.approve()` | Adds a second review where the forge keeps reviews, as GitHub, Forgejo and Gitea do. Where an approval is a vote, sets the same vote, or rejects on GitLab | Look for your review in `threads.reviews()` first |
| `threads.approveAndMerge()` | Approves again, then the merge rejects | Read the pull request, and retry with `merge()` once the approval is in |
| `threads.replyToReviewComment()` | Posts a second reply | Look for your reply in `threads.reviews()` first |
| `checks.report()` | Writes a second check run. A second commit status with the same name takes the place of the first, but GitLab rejects a repeat of a status that is still pending | Retry a commit status, and on GitLab, look for it in `checks.list()` after a failure. For a check run, look for it in `checks.list()` first |
| `checks.rerun()` | Can start another run | Read the check with `checks.get()` first |
| `webhooks.create()` | Registers a second webhook. GitHub rejects a second hook for the same URL | Look for the URL in `webhooks.list()` first |
| `webhooks.redeliver()` | Sends the delivery again | Deduplicate deliveries by their id where you receive them |

### Retry a comment

`upsertComment()` finds a comment by a hidden marker in its body and edits it, or leaves it as it is when it already has the same body, so a retry with the same key edits the comment that an earlier attempt posted instead of posting another. Use one key per change. Pass the key to the first attempt with `comment()`, which writes the same marker in one request. If that attempt fails, retry with `upsertComment()`, and pass the time of the first attempt as `since`, so the retry lists only the comments since then:

```ts
const key = mutation.id
const body = 'Deployed to staging'

if (mutation.attempts === 0) {
  await forge.threads.comment(ref, body, { key })
}
else {
  const since = new Date(mutation.firstAttemptAt.getTime() - 5 * 60_000)
  await forge.threads.upsertComment(ref, { key, body, since })
}
```

Take `firstAttemptAt` before you send the first attempt, and subtract a margin, because the clock of the forge can differ from yours. On GitHub, for issues and pull requests, and on Forgejo and Gitea, the forge filters the comments by `since`. Elsewhere, and for GitHub commit comments and discussions, the provider lists every comment and drops the older ones, so the retry costs a full listing.

This makes a duplicate unlikely, not impossible. A request that timed out on your side can still land on the forge after your retry has listed the comments. Wait before you retry, and longer after a timeout.

### Read before you retry

For the other writes that can repeat, read the current state after the failure, and only send the write again if it is missing. For a merge, pass the head `sha` that you reviewed, so a retry never merges a commit that arrived in between, and read the pull request after any failure:

```ts
try {
  await forge.threads.merge(ref, { method: 'squash', sha: pull.branches?.head.sha })
}
catch (error) {
  const current = await forge.threads.get(ref)
  if (current.state !== 'merged') {
    throw error
  }
}
```

There is no keyed `threads.create()`. Looking for the new thread afterwards needs a listing that shows it at once on every forge, and some forges show a new thread in their listings or their search only after a delay. Before you retry `create()`, list the recent threads of the repository with `threads.list(repo, { author, sort: 'created' })`, and compare their titles with yours.
