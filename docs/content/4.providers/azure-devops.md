The Azure DevOps provider works with Azure Repos pull requests and with Azure Boards work items, which it treats as issues. It also covers pull request statuses, branch policies, repository contents and incoming service hook deliveries. It supports both Azure DevOps Services and Azure DevOps Server, and talks to them through REST API version 7.1, which is exported as `AZURE_DEVOPS_API_VERSION`.

## Authentication

The provider accepts a personal access token or Basic credentials. It sends both as HTTP Basic authentication, using an empty user name for a token. You also have to pass your `organization`:

```ts
import { azureDevOps } from 'forges/azure-devops'

const forge = azureDevOps({
  organization: 'acme',
  auth: { type: 'token', token: process.env.AZURE_DEVOPS_TOKEN! },
}).create()
```

If you leave out `auth`, the provider makes anonymous reads of public data. Azure DevOps sends requests for pull request statuses, policy evaluations and work item queries without credentials to its sign-in page, so an anonymous provider reads pull requests without `checks`, and reports `threads.checks`, `search.threads` and listing work items as unsupported.

## Instance

The `baseUrl` defaults to `https://dev.azure.com`, which makes `dev.azure.com` the instance. To use Azure DevOps Server, set `baseUrl` to the root of the server and `organization` to the collection:

```ts
azureDevOps({
  baseUrl: 'https://tfs.example.com/tfs',
  organization: 'DefaultCollection',
  auth,
})
```

## Repository refs

A repository belongs to a project, and a project belongs to an organization. For this reason, `RepoRef.owner` is `<organization>/<project>`, and `name` is the name of the repository:

```ts
const repo = {
  forge: 'azure-devops',
  instance: 'dev.azure.com',
  owner: 'acme/Widgets',
  name: 'widgets',
} as const
```

Work items belong to a project and not to a repository, so their refs use a namespace ref: `{ owner: 'acme/Widgets', name: '', kind: 'namespace' }`.

## Work items as issues

`threads.create({ kind: 'issue' })` creates a work item of the type `Issue`. If your process template uses a different type, such as `Product Backlog Item`, set the `issueType` option. The tags of a work item are its labels, and `System.AssignedTo` is its single assignee.

## Merging

The provider doesn't read branch policies, so it can't tell which merge strategies are allowed. For this reason, `merge()` requires a `method` and throws `MergeMethodRequiredError` without it. The `fast_forward_only` method isn't available.

`merge()` completes the pull request at its current source commit, and `approveAndMerge()` votes to approve it first. If you pass `whenChecksPass`, `merge()` sets auto-complete on the pull request instead of merging right away.

## Votes as reviews

Azure DevOps has votes instead of reviews, so the provider presents votes as reviews. `threads.reviews()` returns one review for each reviewer who has voted, with the ID `vote:<id>`. A vote of 5 or 10 is `approved`, and a vote of -5 or -10 is `changes_requested`.

`createReview()` votes 10 for `approve` and -10 for `request_changes`. If you pass a body or inline comments, it rejects with `UnsupportedOperationError`.

## Checks

`threads.checks()` returns the statuses of a pull request and the evaluations of its branch policies in one list.

## Webhooks

Azure DevOps service hooks don't sign their deliveries. A service hook subscription can send Basic credentials, though, so set `webhookSecret` to `username:password`. The provider compares it with the `Authorization` header of each delivery. If you don't set `webhookSecret`, no delivery verifies.

```ts
const forge = azureDevOps({
  organization: 'acme',
  webhookSecret: process.env.AZURE_DEVOPS_HOOK_CREDENTIALS,
}).create()

const events = await forge.webhooks.ingest({
  headers: request.headers,
  body: await request.text(),
})
```

You manage service hook subscriptions at the level of the organization and not on a repository, so the management methods of `webhooks` aren't available.
