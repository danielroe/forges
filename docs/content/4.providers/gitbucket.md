First, because the names are almost the same: GitBucket is not Bitbucket. It's a self-hosted Git platform written in Scala, with no relation to Atlassian. GitBucket serves part of GitHub's REST API v3, so the GitBucket provider runs the code of the [GitHub provider](/providers/github) against it, and leaves out what GitBucket doesn't serve. It can read and write issues, pull requests, comments, labels and commit statuses, and it also covers branches, tags, releases and repository webhooks.

## Authentication

The provider accepts a personal access token, which you create under **Account settings > Applications** on your server. GitBucket tokens have no scopes, so a token can do whatever its account can:

```ts
import { gitbucket } from 'forges/gitbucket'

const forge = gitbucket({
  baseUrl: 'https://gitbucket.example.com',
  auth: { type: 'token', token: process.env.GITBUCKET_TOKEN! },
})
```

If you leave out `auth`, the provider makes anonymous reads of public data.

## Instance

GitBucket has no public instance, so `baseUrl` is required. Set it to the root of your server, including the context path if GitBucket runs under one, such as `https://example.com/gitbucket`. The provider appends `/api/v3` itself, and the `instance` in every ref is the host of the server.

## What GitBucket leaves out

GitBucket has no GraphQL, no check runs, no Actions, no reviews, no reactions and no search. It doesn't serve notifications, activity feeds, contributors, branch rules, comparisons, trees or commit comments either. `support()` reports each of those as `false`, or as `'not_applicable'` where GitBucket has no such feature at all, and calling one rejects with `UnsupportedOperationError` before any request goes out. The [capability matrix](/reference/capability-matrix) has the full list.

Some operations that GitBucket does serve still aren't supported, because the provider couldn't do what they promise:

- `threads.setAssignees()` and `setMilestone()`, and `update()`, `close()` and `reopen()` on an issue, need GitBucket to edit an issue, which its API can't do. A pull request is different: `update()`, `close()` and `reopen()` work, for its title, body and state. An update that also sets labels or assignees rejects with `UnsupportedOperationError`, so set the labels with `setLabels()`.
- `threads.deleteComment()` deletes the comment, but GitBucket answers with the comment's id as the HTTP status code, so the provider can't tell whether it worked.
- `repos.collaborators()` would list every collaborator without a role, and `repos.addCollaborator()` fails with a `500` for the roles that GitHub has beyond read, write and admin.
- `releases.create()` creates a release without its tag and drops `draft`, `prerelease` and `target`, while `releases.update()` needs the whole release.
- `webhooks.update()` and `webhooks.rotateSecret()` need the whole hook, while the provider sends only what changes.

## Listing threads

GitBucket lists issues and pull requests apart, so pass `kind` to `threads.list()`. Without it, you get the issues and a `kind_unsupported` warning. GitBucket returns 25 threads to a page, whatever `perPage` asks for, and filters milestones by their title. It has no `since` or `involves` filter, so those come back with a `filter_unsupported` warning.

`threads.getMany()` reads each thread on its own, since GitBucket has no GraphQL to batch the reads with.

## Commits

GitBucket skips commits from the second page of a listing on, so `commits.list()` returns a single page. When that page is full, the result has no cursor and carries a `commits_truncated` warning. To see further back, narrow the listing with `since`, `until` or `path`, or raise `perPage`, up to 100.

## Checks

GitBucket has commit statuses but no check runs, so the `checks` of a pull request are its statuses, and their `url` is the pull request's page, where GitBucket shows them.

## Releases

GitBucket gives a release no id, so the `id` of a release ref is its tag. `releases.get()` reads the release by that tag.

## Merging

GitBucket doesn't report which merge methods a repository allows, so pass a `method` to `merge()`, or it throws `MergeMethodRequiredError`. GitBucket ignores the head a merge expects, so `sha` rejects with `UnsupportedOperationError`. It also reports no merge commit, so the result has no `sha`.

## Webhooks

GitBucket signs its deliveries like GitHub, with `X-Hub-Signature-256`, so `webhooks.verify()` and `webhooks.ingest()` work as they do on GitHub. It sends comments, review comments, issue and pull request changes, pushes, new branches and tags, and wiki edits, so `webhooks.create()` subscribes only to those. It accepts a few more event names that it never sends, and answers a name it doesn't know with a `500`.
