The Upstream provider works with [upstream.codes](https://upstream.codes). Upstream serves GitHub's REST API at `/api/v3`, so this provider runs the code of the [GitHub provider](/providers/github) against it and leaves out what Upstream doesn't serve. Upstream calls pull requests change requests, and they are `pull_request` threads here. Refs from this provider have `forge: 'upstream'`.

## Authentication

The provider accepts a personal access token, which starts with `upt_`. Create one under [**Settings > API tokens**](https://upstream.codes/settings/tokens) and grant it the scopes for what you call, such as `issues:write` and `changes:write`:

```ts
import { upstream } from 'forges/upstream'

const forge = upstream({
  auth: { type: 'token', token: process.env.UPSTREAM_TOKEN! },
})
```

If you leave out `auth`, the provider makes anonymous reads of public data. Upstream lists the users a thread can be assigned to only with a token.

## Instance

The provider talks to `https://upstream.codes/api/v3` by default. The same API is also served at `https://api.upstream.codes/api/v3`, and either host gives refs with `instance: 'upstream.codes'`, so links point at upstream.codes. To use another Upstream instance, set `baseUrl` to its root; the provider appends `/api/v3` itself.

## Web URLs

Upstream calls pull requests change requests and serves them at `/{owner}/{name}/changes/{number}`, which `urlFor()` builds and `parseUrl()` reads. Issues and change requests share one sequence of numbers. A release page is addressed by an id that the API doesn't return, so `urlFor()` has no link for a single release.

## What Upstream leaves out

Upstream has no GraphQL, so the operations that go through it on GitHub aren't supported: closing references, subscriptions, hiding comments, marking duplicates, review threads and committing files. Its REST API has no collaborators, contributors, teams, branch rules, timelines, commit comments, activity feeds of accounts, commit search or security alerts either. `support()` reports each of those as `false`, or as `'not_applicable'` for milestones and issue types, which Upstream doesn't have, and calling one rejects with `UnsupportedOperationError` before any request goes out. The [capability matrix](/reference/capability-matrix) has the full list.

Discussions on Upstream aren't served through GitHub's API, so no operation takes a discussion.

## Reviews

Upstream stores approvals, change requests and comment reviews, but no pending reviews. `threads.approve()` works, and `threads.createReview()` works when you pass an `event`. Without one, it rejects with `UnsupportedOperationError`, and `threads.submitReview()` isn't supported. Upstream has no endpoint for the comments of one review or for replies to a review comment, so `threads.getReview()` reads the review from the list of the change request's reviews.

## Updating a branch

Upstream updates the branch of a change request only when the change request mirrors a GitHub pull request, so `threads.updateBranch()` isn't supported.

## Releases

Upstream creates no tag for a release, so push the tag, or create it with the git refs API, before `releases.create()`.

## Notifications

`notifications.markAllRead()` marks every notification read. Upstream can't mark only those of one repository, so passing `repo` rejects with `UnsupportedOperationError`. Upstream has no endpoint to unsubscribe from a notification thread.

## Search

Upstream searches code in one repository at a time, so `search.code()` needs a `repo`, and without one rejects with `UnsupportedOperationError` before any request goes out. Upstream reports every code search as incomplete, so its pages carry no `search_incomplete` warning.

## Webhooks

Upstream signs its deliveries like GitHub, with `X-Hub-Signature-256`, and sends them under GitHub's event names, so `webhooks.verify()` and `webhooks.ingest()` work as they do on GitHub. Upstream keeps the deliveries of each hook, which `webhooks.deliveries()` lists.
