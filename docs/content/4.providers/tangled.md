The Tangled provider works with [Tangled](https://tangled.org), a forge built on atproto. It can read and write issues, pulls, comments, labels, assignees, reactions and collaborators, merge pulls, read profiles, read repository contents from the mirror of each repository's knot, manage spindle webhooks, stream live events from Jetstream and verify incoming webhook deliveries. Tangled has no reviews, releases or security alerts, so those capabilities are `'not_applicable'`.

## Authentication

Reading is public and needs no credentials. Writing requires an atproto session, which you get from an app password or from an OAuth client:

```ts
import { tangled } from 'forges/tangled'

const reader = tangled({})

const writer = tangled({
  auth: {
    type: 'app_password',
    identifier: 'alice.example.com',
    password: process.env.TANGLED_APP_PASSWORD!,
  },
})
```

With `app_password`, the provider creates a session on the PDS (personal data server) of the account. It looks for the PDS in this order:

1. The `pds` option, if you pass it.
2. The DID document, if `identifier` is a DID.
3. `https://bsky.social`.

With `oauth`, you pass the `did`, the `pds` and a `fetch` from an atproto OAuth client that signs requests:

```ts
tangled({
  auth: {
    type: 'oauth',
    did: session.did,
    pds: session.pds,
    fetch: session.fetch,
  },
})
```

## Instance and services

The `baseUrl` defaults to `https://tangled.org`. The provider uses it for web links and as the instance.

Tangled records are stored on many servers, so the provider has to read from several services. You can change each one of them with an option:

| Option | Reads | Default |
| --- | --- | --- |
| `plcUrl` | DID documents, to find the PDS of each author and the knot of each repo | `https://plc.directory` |
| `handleResolverUrl` | The DID for a handle, when the `owner` of a ref is a handle | `https://public.api.bsky.app` |
| `jetstreamUrl` | The live event stream | A public Bluesky Jetstream instance |
| `apiUrl` | `request()`, the index that serves every read, and the mirror that serves git contents | `https://api.tangled.org` |
| `sshHosts` | The host that accepts git over SSH, per knot | `knot1.tangled.sh` maps to `tangled.org` |
| `notificationsUrl` | The notification service, when `notifications` is enabled | None |

The index at `apiUrl` lists the records of every repository, and can lag behind the knot that hosts them. The provider waits for the index to have a record it just wrote, so a write is immediately visible to a read.

## Refs and numbers

Issues and pulls are `org.tangled.track.ticket` records, and a thread is identified by the key of its ticket record, which is the number that Tangled shows. In a `ThreadRef`, the `number` is the record key and `externalId` is the ticket's AT-URI, whose repository survives a rename. The `owner` of a repo is the DID of its owner, and `RepoRef.externalId` is the DID of the repo.

In the refs that the provider returns, the `name` of a repo is the name it is addressed by. You can pass a ref that has a handle as `owner` and the same name, which is what `parseUrl()` returns for a URL such as `https://tangled.org/@acme.example.com/widgets`. The provider resolves the handle, so the ref that it returns can differ from the one you passed.

`parseUrl()` reads repository pages and the pages for threads (`/issues/{number}` and `/pulls/{number}`), commits (`/commit/{sha}`), files (`/blob/{ref}/{path}`) and comparisons (`/compare/{base}...{head}` or `/compare/{base}..{head}`).

Tangled names a repository by the handle of its owner, so the provider reads the handle from the owner's DID document and reports it as `RepoRef.ownerHandle` and as the `login` of `Repo.owner`. The `owner` stays the DID, so that a repository is found the same way whichever is known. An owner whose DID document claims no handle is named by its DID, which Tangled redirects to the handle.

`repos.byOwner()` lists the repositories of an account, which you name by its handle or DID, from the index. Every Tangled repo is public.

`repos.get()` also reports `stars` and `forks`, from `org.tangled.feed.countStars` and `org.tangled.repo.countForks` on the index at `apiUrl`. The index can lag behind the knot, so these counts can be lower than the ones in the Tangled UI. Each count is absent when the index can't return it. Listings of repositories don't include them.

## Thread numbers

A thread's number is the key of its ticket record on the repository's knot, and the same key addresses its pages, so `Thread.url` and the URLs of comments point at the page that the record names.

In text, a thread is mentioned as `#<number>`. `urlFor()` links a thread by that number, and `referenceFor()` writes it back as `#<number>`, or `owner/name#<number>` for another repository, with the owner's handle where the ref carries one.

## Thread state

A ticket stores its own state, and the author of the thread, the owner of the repo or a collaborator may change it. If any other account calls `close()` or `reopen()`, the call throws `InsufficientScopeError` and writes nothing.

`close()` and `reopen()` write the new state to the ticket's record and read the thread again, so they resolve with what they wrote even while the index still lists the earlier state.

A completed pull request is a merged one, and a completed issue has the `stateReason` `completed`. `close()` with `reason: 'completed'` closes an issue as completed; any other close is a plain `closed`.

## Labels and assignees

Labels are `org.tangled.label.definition` records on the knot of the repo, and a ticket's labels are the `tangledLabels` of its record, which name definitions by their keys.

Each call to `setLabels()`, `addLabels()`, `removeLabels()` or `setAssignees()` writes a new version of the ticket with the labels or assignees it leaves, so the thread reads back the change immediately. A name must match a label definition of the repository, or the call throws `NotFoundError`. A call that would leave the record unchanged writes nothing, because the knot refuses one. `createLabel()` writes a definition on the repository's knot, so only the owner of the repo can call it.

`repos.collaborators()` lists the owner of the repo with the role `admin` and each collaborator with the role `write`. `permissionFor()` returns `read` for any other account, because every Tangled repo is public.

## Comments and reactions

Comments live on the knot of the repository. `threads.comments()` lists them from the index and names the account that wrote each version; `getComment()` reads one from the knot itself. `createComment()`, `updateComment()` and `deleteComment()` write to the knot, which decides who may change a comment.

Reactions are records in the account's own repository on its PDS. `threads.reactions()` lists them from the index with the account that made each one; `react()` and `unreact()` write and delete the account's own records.

## Listing threads

`threads.list()` asks the index to search the repository for tickets, and every listing pages by the index's cursor. Tangled sorts threads by when they were created, so a `sort` of anything else brings a `sort_unsupported` warning, and filters that the search has no word for bring `filter_unsupported` warnings.

`search.threads()` uses the same search: free text plus the Tangled qualifiers (`is:open`, `is:closed`, `is:merged`, `author:`, `assignee:`, `label:`), a `repo` to narrow to, and `since`. It ignores `owner` and `involves` with a `filter_unsupported` warning. Tangled searches repositories with `search.repos()`, matching the manifest records.

## Repository contents

The `contents` verbs read files, trees, branches, tags and commits from the index's mirror of each repository's knot, so they need no credentials. The mirror lists one level of a tree at a time, so `tree()` with `recursive` returns one level and a `recursive_unsupported` warning. The mirror filters commits by path but not by author or date, so `commits()` ignores `author`, `since` and `until`, and warns with `filter_unsupported`.

A pull carries its changes as a range of commits rather than as a branch. `threads.files()` and `threads.commits()` read the round of the latest `org.tangled.review.patch` and show the range it spans. When several commits in the round change the same file, that file's counts and patch are those of each commit together, and the listing has a `files_approximate` warning.

## Notifications

Notifications use the `org.tangled.temp.notification.*` lexicons. These lexicons are in Tangled's temporary namespace and can change. To enable notifications, pass `auth` and set `notificationsUrl` to the base URL of the notification service. Listing and counting notifications are `'experimental'`; marking them read is `'unverified'`.

Stars and follows have no thread. They appear with `kind: 'other'`, and `typeRaw` contains the type of the notification.

## Pulls and merging

A pull request is a ticket with a target branch and a round: an `org.tangled.review.patch` that names the commits the head has and the base lacks. `threads.create()` with `kind: 'pull_request'` writes the ticket, asks the index's mirror for the merge base of `base` and `head`, and submits the round to the knot. If the knot refuses the round, the ticket is erased again, so there is no pull without one. `head` must be a branch of the same repository; pulls from forks and drafts aren't supported.

`merge()` asks the index's mirror to merge the head commit of the latest round onto the target branch, with a merge commit (the default) or a rebase, and then marks the ticket completed. `title` and `message` make up the merge commit's message; a rebase ignores them. Only the owner of the repository or a collaborator can merge.

`repos.addCollaborator()` writes a collaborator record on the repository's knot. Tangled has a single collaborator role, so `role` must be `write`.

## Subscriptions

`threads.subscribe()` writes an `org.tangled.feed.subscription` record to the account's own repository, and `unsubscribe()` deletes it. A subscription with `ignore` set is a mute.

## Live events

`sources.stream()` streams events from Jetstream, and each item has a `cursor`. To resume a stream later, save the cursor and pass it back:

```ts
for await (const { event, cursor } of reader.sources.stream({
  cursor: saved,
  signal,
})) {
  console.log(event.kind, event.summary)
  saved = cursor
}
```

To close the connection, abort the signal or break out of the loop. If the connection drops, the iterator throws `StreamClosedError` with the last cursor. The provider doesn't reconnect by itself, so call `stream()` again with that cursor.

## Activity feeds

An account's issues, pulls, comments and reactions are records on the account's own PDS or on the knots of its repositories, and the index lists them by author. `users.events()` merges those listings by record key, which orders them by when they were written. The events are the ones `sources.stream()` yields for the same records, with `source: 'poll'`.

The first page's `etag` digests the records on the page. Pass it back as `cursor: { etag }`, with the same `perPage`, and you get a `notModified` page when nothing on it changed.

Tangled has no feed of a repository's activity, so `repos.events()` isn't available.

## Webhooks

To verify deliveries, set `webhookSecret` to the secret that you configured on the hook:

```ts
const forge = tangled({
  webhookSecret: process.env.TANGLED_WEBHOOK_SECRET,
})

const events = await forge.webhooks.ingest({
  headers: request.headers,
  body: await request.text(),
})
```

With each delivery, Tangled sends these headers:

| Header | Content |
| --- | --- |
| `X-Tangled-Signature-256` | `sha256=` followed by the hex HMAC-SHA256 of the body |
| `X-Tangled-Event` | The event name |
| `X-Tangled-Delivery` | The delivery ID |

A `push` delivery becomes a `push` or `ref` event. A `pull_request:*` delivery names its pull request only by a number the spindle always sends as `0`, so the event carries a snapshot of the pull request but no thread. A `repository:renamed` delivery becomes an `other` event with the old and new names.

The management methods of `webhooks` list, create, update and delete the hooks that the repository's spindle delivers, and read and re-send its deliveries. They authenticate with a service token from the account's PDS. A hook can only subscribe to what Tangled delivers (pushes, renames and pull requests), so `create()` throws `UnsupportedOperationError` when none of the requested `events` maps to one.
