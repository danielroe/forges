The Sourcehut provider works with [Sourcehut](https://sr.ht), a suite of small services that share one account and one OAuth 2.0 token. Reading a repository uses `git.sr.ht`, its issues use `todo.sr.ht`, its patches use `lists.sr.ht`, its builds use `builds.sr.ht`, and accounts use `meta.sr.ht`. The provider fans requests out across those services for you and normalises them into the shared [data model](/concepts/data-model).

## Authentication

Create a [personal access token](https://meta.sr.ht/oauth2) and grant it the scopes of the services you need, one grant per service and scope, such as `git.sr.ht/REPOSITORIES:RO` or `todo.sr.ht/TICKETS:RO`. The provider sends the token as `Authorization: Bearer <token>`:

```ts
import { sourcehut } from 'forges/sourcehut'

const forge = sourcehut({
  auth: { type: 'token', token: process.env.SOURCEHUT_TOKEN! },
})
```

An OAuth 2.0 bearer token works too. Every service refuses reads without a token, so unlike most providers there are no anonymous reads.

## Instance

The `baseUrl` defaults to `https://sr.ht`. Each service is a subdomain of that host, so `https://sr.ht` gives `git.sr.ht`, `todo.sr.ht`, `lists.sr.ht`, `builds.sr.ht` and `meta.sr.ht`. On a self-hosted instance, set `baseUrl` to the instance root and the services are derived the same way.

Sourcehut usernames are written with a leading tilde, so a repository ref's `owner` is `~sircmpwn` and a slug is `~sircmpwn/scdoc`.

## Repositories and contents

`repos.get()`, `repos.list()` and `repos.byOwner()` read `git.sr.ht`. `contents.getFile()`, `contents.tree()`, `contents.branches()`, `contents.tags()`, `contents.resolveRef()`, `commits.list()` and `commits.get()` read the same service. Sourcehut has no compare resolver, so `contents.compare()` is unsupported.

`repos.labels()` and `repos.permissionFor()` are `'emulated'` from the repository's `todo.sr.ht` tracker and its `git.sr.ht` access list. The access list is served only to the repository's owner and collaborators, so for anyone else `permissionFor()` falls back to what the repository's visibility allows. Sourcehut has no milestones, contributors, contributors statistics, assignable users or reviewer candidates.

## Issues

Issues live in a `todo.sr.ht` tracker whose name matches the repository, so `~sircmpwn/scdoc` reads the tracker `~sircmpwn/scdoc`. `threads.get()`, `threads.list()`, `threads.comments()`, `threads.events()` and `threads.getMany()` all work on them, and `threads.subscription()` reports whether the account is subscribed.

Comments are the comment entries of a ticket's events, which is the endpoint the API exposes. Sourcehut has no reactions and no comment editing over the API.

## Patchsets

Sourcehut's equivalent of a pull request is a patchset on a mailing list. There is no way to tell which list belongs to a repository, so a patch ref's `repo` names the **mailing list**, not the git repository. `threads.get()` reads a patchset by id, `threads.list()` lists a list's patchsets, and `threads.comments()` and `threads.events()` read the replies to its thread. Patchsets carry no reviews, files, commits or checks.

## Builds

`builds.sr.ht` lists the builds of the authenticated account, not of one repository, so `ci.runs()` is `'emulated'` and warns that it ignores the repository. `ci.getRun()` reads one build, `ci.jobs()` lists its tasks, and `ci.log()` streams a task's log. A job ref must name its run, because a task has no top-level resolver.

## Accounts

`users.get(login)` and `users.me()` read `meta.sr.ht`. Both need the token, because `meta.sr.ht`'s account resolvers reject a token on the anonymous query and require one on the authenticated query. Sourcehut has no sponsorship, follow feeds or repository events.

## Webhooks

Sourcehut signs deliveries with its own ed25519 key rather than a shared secret: `X-Payload-Signature` is the signature of the raw body followed by the `X-Payload-Nonce` header. The provider verifies it against the instance's published public key, which defaults to `sr.ht`'s and can be overridden with `webhookPublicKey` for another instance.

Because a Sourcehut webhook sends the result of a GraphQL query that you register with it, the provider translates the shape it documents for repository and push events. Managing hooks is not implemented.
