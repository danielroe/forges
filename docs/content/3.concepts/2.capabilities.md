Forges don't offer the same features. Bitbucket has no releases, for example, and Tangled has no checks. Rather than letting you find out by trial and error, every provider declares what its forge supports in `provider.capabilities`. This page explains what the declarations mean, so you know what to expect when you check one.

## Support levels

Each entry has one of five values, which tell you how much you can rely on the operation:

| Value | Meaning |
| --- | --- |
| :capability-level[`true`]{level="native"} | The forge supports it natively, and a test verifies it against the forge's own responses. |
| :capability-level[`'experimental'`]{level="experimental"} | Verified like `true`, but built on an API that the forge marks as unstable or in preview, so it can change. |
| :capability-level[`'emulated'`]{level="emulated"} | The forge has no such operation, so the provider composes it from other calls. Its behaviour can differ from a native operation. |
| :capability-level[`'unverified'`]{level="unverified"} | The provider implements it, but no test has verified it against the forge's responses yet, so it may not work. |
| :capability-level[`false`]{level="none"} | Not available. Calling it rejects with `UnsupportedOperationError`. |

The forge's own responses are either a [recording of the live forge](/contributing/record-fixtures) or a fixture written from the forge's documentation. We check on every commit to `forges` that each level above `'unverified'` has such a test, and that nothing such a test verifies stays `'unverified'`.

Forgejo has no done state for notifications, for example, so its `notifications.markDone` is `'emulated'`. To get as close as possible, the provider marks the notification as read and unsubscribes you from the thread.

::

## Per thread kind

Support can also differ between kinds of threads. GitHub can close issues, pull requests and discussions, whereas Cursor Origin only has pull requests. For operations like these, the entry is an object with a value for each kind, and `can()` takes the kind as a second argument.

## Experimental providers

Sometimes it isn't a single operation that can change, but the forge's API as a whole. Then `capabilities.experimental` is `true`. Cursor Origin, Pushin.eu and Tangled are experimental providers at the moment: Cursor Origin uses an alpha API, and the APIs of Pushin.eu and Tangled are still young.

## Version-dependent support

Some capabilities depend on the version of the instance. GitHub Enterprise Server, for instance, supports marking notifications as done from version 3.13. Because the provider works out its capabilities without sending a request, it can't read the version by itself. Pass `instanceVersion` if you know it, or call `refreshCapabilities()` to let the provider find out.

## Anonymous providers

Capabilities also depend on credentials. An anonymous provider reports `false` for writes, notifications and subscriptions, and also for any read that the forge only serves to signed-in users. For example, GitLab only shows labels and milestones to signed-in users, so `can('repos.labels')` is `true` with a token and `false` without one. To see what each forge supports without credentials, turn on **Without credentials** in the [capability matrix](/reference/capability-matrix) or on a provider page.

## Using capabilities

Capabilities are useful in a few ways:

- Call [`provider.can()`](/guides/capabilities) before an operation that a forge might lack.
- Use the [capability matrix](/reference/capability-matrix) to decide which forges your tool can support.
- Read the `limits` entry for the text limits of a forge, such as the maximum length of a comment.
