A `ForgeEvent` describes something that happened on a forge, such as a comment, a push, a review or a label change. Forges tell you about these changes in different ways, so providers produce events from three sources:

| Source | How it works | Capability |
| --- | --- | --- |
| `webhook` | The forge sends an HTTP request to your server. | `sources.webhook` |
| `poll` | You list notifications or activity feeds on a schedule. | `sources.poll`, `repos.events`, `users.events` |
| `subscribe` | You keep a connection open and receive events as they happen. | `sources.subscribe` |

Whichever source an event came from, `event.source` tells you. Most forges support webhooks, and every forge that lists notifications can also be polled, so `sources.poll` follows `notifications.list`. Activity feeds have capabilities of their own. Tangled is the exception that offers `subscribe`, through Jetstream.

## Shape of an event

An event has the same fields whatever its source:

| Field | Content |
| --- | --- |
| `kind` | What kind of thing happened, such as `comment`, `review`, `state_change`, `label`, `push` or `release` |
| `action` | The verb, such as `opened`, `closed`, `merged`, `created` or `labelled` |
| `summary` | One line that suits a list row |
| `actor`, `repo`, `thread` | Who did it, and where, when the event has them |
| `isPublic` | Whether anyone can see the event, when the forge says. Activity feeds on GitHub, Forgejo and Gitea report it |
| `detail` | Typed fields for the kind, discriminated by `detail.type` |
| `occurredAt` | A `Date` |
| `payload` | The unnormalised delivery |

To see which kinds and actions each forge delivers, and which fields each `detail.type` has, look at the [events reference](/reference/events).

## Raw names stay available

The normalised `kind` and `action` are derived from the forge's own event name and verb, and those stay available in `kindRaw` and `actionRaw`. If a forge uses wording that has no equivalent in the shared model, `action` is `other`, and the raw name still tells you what happened.

GitLab needs a special mention here. For some changes to a thread, the event kind comes from the text of a system note and not from a field of its own, which makes it a best guess. For this reason, the GitLab provider reports `eventKinds: 'heuristic'` in its capabilities. If it doesn't recognise a note, `kind` can be `other`, while `kindRaw` and `payload` remain exact.

## Activity feeds

When you want to know what happened in a repository, or what an account did, without registering a webhook, read the forge's activity feed. `repos.events()` lists the activity of a repository, and `users.events()` lists the activity of an account across the repositories that the credential can see. Both return events with `source: 'poll'`, in the order the forge added them to its feed, latest first:

```ts
for await (const event of gh.users.events('octocat')) {
  console.log(event.occurredAt, event.repo?.name, event.summary)
}
```

A feed covers what the forge records in it, which differs by forge. It usually has pushes, new and deleted branches and tags, issues and pull requests that were opened, closed or merged, comments and reviews. A feed event has the same `kind`, `action`, `thread` and `detail` as the webhook delivery for the same change. An activity without a shared kind, such as a star or a fork, has `kind: 'other'`, and `kindRaw` names it.

Feed items are often smaller than webhook deliveries. A GitHub push, for example, can leave out its commits, and a GitLab push names only the newest one, so trust `detail.commitCount` over `detail.commits.length`. When you want the rest, hand the push's `before` and `after` to `contents.compare()`. The provider normalises what the feed contains and doesn't send more requests to fill in the rest. To poll a feed without paying for an unchanged page, see [Poll for changes](/guides/pagination#poll-for-changes).

## Subscriptions

`sources.subscribe()` returns an async iterable of `{ event, cursor }`. To pick up where you left off after a restart, save the cursor and pass it back when you subscribe again. The provider doesn't reconnect when the connection drops. Instead, it throws `SubscriptionClosedError` with the last cursor, and you call `subscribe()` again:

```ts
for await (const { event, cursor } of reader.sources.subscribe({
  cursor: saved,
  signal,
})) {
  console.log(event.kind, event.summary)
  saved = cursor
}
```
