Every provider lists the kinds and actions that its webhook deliveries translate into in `webhooks.events`, and the matrix on this page is built from that list. If you want to know what an event looks like, read [Events](/concepts/events). The following example checks whether a provider can deliver label events:

```ts
const labels = provider.webhooks.events.some(
  event => event.kind === 'label' && event.action === 'labelled',
)
```

The matrix covers webhook deliveries. Events from `threads.events()` and `sources.subscribe()` use the same kinds, but providers don't list which ones they produce. A kind that is declared without an action, shown as `any`, can arrive with any action, including `other`. Whatever the kind, `kindRaw` and `actionRaw` always keep the names that the forge itself uses.

## Event times

A webhook event's `occurredAt` comes from the first of these timestamps that its payload has. When it has none, or when the event is a deletion, the event has `undated: true` and `occurredAt` is the time the delivery reached `forges`:

| Forge | Timestamps, in order | Undated deliveries |
| --- | --- | --- |
| GitHub | `created_at` of an opened thread, `merged_at` or `closed_at` of a closed one, the comment's `created_at` or, when edited, `updated_at`, the review's `submitted_at`, the release's `published_at` when published, the star's `starred_at`, the new fork's `created_at`, the repository's `pushed_at` for a push and its `updated_at` for a rename, transfer, archive or visibility change, then the thread's `updated_at` | Pings, deletions, branch and tag creation, installations, memberships, `watch` stars, wiki edits and release actions other than publishing |
| GitLab | `created_at` of an opened thread, `closed_at` of a closed issue, the note's `created_at` or, when updated, `updated_at`, the release's `created_at` when created, the newest commit's `timestamp`, the member's `created_at` when added, then `updated_at` | Pushes without commits, removed members, wiki edits and release updates and deletions |
| Bitbucket | The pull request's `created_on` when created, the comment's `created_on` or, when updated, `updated_on`, the approval's or the request for changes' `date`, the newest commit's `date`, then the pull request's `updated_on` | Deleted comments, renames, transfers, forks and branch or tag changes without commits |
| Forgejo, Gitea | `created_at` of an opened thread, `merged_at` or `closed_at` of a closed one, the comment's `created_at` or, when edited, `updated_at`, the release's `published_at` when published, the new fork's `created_at`, the head commit's `timestamp`, then the thread's `updated_at` | Deletions, branch and tag creation, pushes without commits, wiki edits and release actions other than publishing |
| Gitee | `created_at` of an opened thread, `merged_at` of a merge, `closed_at` or `finished_at` of a close, the comment's `created_at`, then the thread's `updated_at`, or the head commit's `timestamp` for a push | Branch and tag changes without commits |
| Azure DevOps | The event's `createdDate` | Events without one |
| Cursor Origin | The event's `eventTime` | Events without one |
| Tangled | The pull's `created_at` when it is created | Every other delivery |
| Sourcehut | The delivery's `date`; the event's `created` or the email's `received` for a thread's timeline | Deliveries whose query omits `date`, and timeline entries without a `created` |

A push takes the time of its newest commit where the forge doesn't report when the push happened, so a push of older commits can be dated before it happened. Tangled sends no time for a change other than a new pull: its `repository.updated_at` is the time the repository was created.

## Detail and native events

`detail.type` tells you which fields an event carries, so narrowing on it gives you a typed `detail`. The `repo` kind has a separate detail type for each kind of change. An event whose kind has no detail type has no `detail` at all.

When you register a webhook, `webhooks.create({ events })` translates each kind into the event names of the forge, and `webhook.events` maps them back again. If you need a forge event that has no kind, subscribe to it by name with `nativeEvents`. The following table lists the detail type and fields of each kind:
