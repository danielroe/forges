Thanks for helping with `forges`. This page covers how to set up the repository, the checks a change has to pass and the rules that keep the providers consistent. By taking part, you agree to the [Code of Conduct](https://github.com/danielroe/forges/blob/main/CODE_OF_CONDUCT.md).

## Set up

You need Node.js 22.18 or later and [pnpm](https://pnpm.io). The repository pins the versions it develops with in `devEngines`.

```sh
pnpm install
pnpm test:unit
```

## Project layout

| Path | Content |
| --- | --- |
| `src/<forge>/` | One provider each: its factory, normalisation and webhook handling |
| `src/model.ts`, `src/provider.ts`, `src/define.ts` | The shared model, the provider interface and `defineForgeProvider()` |
| `src/kit.ts` | The `forges/kit` entry: what provider authors import |
| `src/fake/`, `src/testing/` | The in-memory forge and the test helpers |
| `test/` | Unit tests, recorded fixtures and the shared recording steps |
| `examples/` | Small, tested projects that use the library |
| `docs/` | The documentation site |

## Rules

- Declare a capability `true` only when a test calls it. Use `'experimental'` for anything that isn't verified against a recording of the live forge.
- After you change a provider's capabilities, run `pnpm capability-matrix`. A test fails if the docs are out of date.
- Import source files with the `.ts` extension, so that `node scripts/<name>.ts` runs without a build.
- Don't add runtime dependencies. Don't import Node.js built-in modules from a provider.
- Keep errors, warnings and `skipped` reasons free of credentials.
- Add a test for each change. For a new read, record a fixture instead of writing one by hand.

To add a forge or an operation, read [Write a provider](/contributing/write-a-provider) and [Record fixtures](/contributing/record-fixtures).

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org). Releases are cut from the commit messages, so the type decides the version bump. Use the provider as the scope when a change concerns one forge:

```text
feat(github): adopt asynchronous direct merges
fix(gitlab): read nested group paths
docs: explain webhook verification
```

Use the same format for the title of a pull request.

## Pull requests

- Keep a pull request to one change.
- Run `pnpm check:all` before you push. CI runs the same checks.
- Describe what changed and why. Link the issue it closes.

## Writing documentation

The documentation lives in `docs/content`. Write short sentences in the second person, and prefer a code example to a long explanation. Avoid em-dashes and filler words. Run the site locally with:

```sh
pnpm --filter forges-docs dev
```

The steps in the credentials picker on [Configure from the environment](/guides/environment) live in `scripts/credential-steps.ts`. To verify a step, check it against the forge's documentation, or against its source repository when the site is unavailable. Then add the URLs to `sources` and the date to `verified`. For a fact about `forges` itself, cite the path of the source file or page. The picker marks steps without `verified` as unverified, and `pnpm test:unit` lists them as to-dos.

Comments on exported declarations in `src` appear in the [API reference](/reference/overview) and the [provider kit](/contributing/provider-kit). To change a page there, change the comment. `scripts/api-docs/config.ts` sets where a symbol appears, and a test fails for an export that no page selects.

Write comments in the style of the rest of the reference:

- Describe what the code does now. Leave out history and plans.
- Start a method or function with a verb in the third person: "Lists the threads of a repository." Describe a property with a noun phrase, and a boolean with "Whether…" when it needs a sentence.
- Leave a property without a comment when its name says it all, such as `title` or `createdAt`. Every export and every method needs one.
- Put a default in `@default`, without backticks: `@default 'open'`. Write a default that is not a literal in the sentence.
- Describe a parameter with `@param name Description` when its name and type don't say what it is. Add `@returns` for a value that needs explaining, and `@throws` for an error that a caller should handle.
- Give the main entry points an `@example` with a fenced `ts` block. Keep it to the shortest code that works.
- Link with `{@link Name}`. A name that the reference does not document becomes plain code.

`raw`, `payload` and the `...Raw` properties of the data model are left out of the pages, and the Data model page describes them once. `pnpm docs:api --list` shows what still has no description.

## Reporting a problem

Open an [issue](https://github.com/danielroe/forges/issues) with steps to reproduce. For a forge-specific bug, name the forge and, for a self-hosted forge, its version.
